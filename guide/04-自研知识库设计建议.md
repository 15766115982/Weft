# 04 · 自研知识库设计建议

> 综合 [01 Obsidian 架构解析](./01-obsidian-架构解析.md)、[02 开源替代品代码分析](./02-开源替代品代码分析.md)、[03 关键技术专题](./03-关键技术专题.md) 三篇调研,给出自研个人/项目知识库的落地架构建议。

## 一、先回答三个根本问题

写代码之前,先想清楚这三件事——它们决定了 80% 的架构:

### 1. 事实来源(source of truth)是什么?

调研的 8+ 个项目只有四种答案:

| 方案 | 代表 | 换来 | 代价 |
|---|---|---|---|
| **纯 Markdown 文件** | Obsidian、Foam、SilverBullet | 生态、可读性、"file over app" 用户信任 | 查询性能靠索引层补 |
| 数据库(SQLite) | Joplin、Logseq DB 版 | 查询与性能 | 可读性、第三方工具生态 |
| 结构化文档 + 可重建索引 | 思源(.sy JSON + SQLite) | 折中,最务实 | 双写映射复杂度 |
| CRDT 文档即数据库 | AFFiNE、Anytype | 协作原生 | 复杂度最高 |

> **建议:个人/项目知识库选纯 Markdown 文件 + YAML frontmatter。** 这是用户信任的基石,也是 Obsidian 成功的核心。Logseq 从文件版转向 DB 版的教训是"双写映射复杂度可能超过直接上数据库"——除非你确定要做块级模型,否则不要复制这条路。

### 2. 链接用什么做锚?

- ❌ 标题/路径为锚(Obsidian 式 wikilink):重命名要付出工程代价(遍历倒排索引重写所有引用),但**用户建链成本最低**
- ✅ 不可变 ID 为锚(思源块 ID、TiddlyWiki 对象引用):重命名/移动/同名问题一次性消灭

> **务实折中(推荐 Obsidian 兼容路线)**:显示层用 `[[basename]]` 短链(用户体验好),索引层维护 `basename → paths` 映射 + 重命名时自动重写引用。若做项目知识库且需要块级引用,学 Obsidian 的 `^block-id` 显式标注,不要做 Roam 式隐式块数据库。

### 3. 用户规模与协作需求?

```
单人单机     → 不需要同步层(Git 即可)
单人多端     → 文件级同步(Syncthing / Git 三路合并)
多人协作     → 才需要 CRDT(Yjs)
```

> **不要为单人场景过早引入 CRDT**——这是调研中最一致的忠告。

## 二、推荐架构(对标 Obsidian,吸取各家之长)

```
┌─────────────────────────────────────────────────────┐
│                    UI 层 (Web 技术栈)                 │
│   文件树 │ 编辑器(CM6)│ 反链面板 │ 图谱 │ 搜索      │
├─────────────────────────────────────────────────────┤
│                   插件系统(一切皆插件)                │
│   核心功能 = 核心插件,与社区插件走同一套 API           │
├─────────────────────────────────────────────────────┤
│                  Metadata Cache(内存索引)            │
│   正排链接表 │ 倒排反链表 │ 标签表 │ 块ID表 │ 别名表  │
├──────────────────┬──────────────────────────────────┤
│   索引管线(Worker) │        全文搜索                  │
│   remark/mdast    │   SQLite FTS5 + 中文预分词        │
│   + wikilink 扩展  │                                 │
├──────────────────┴──────────────────────────────────┤
│              平台适配层(薄壳,可替换)                  │
│   fs 抽象 │ 文件 watcher(chokidar)│ 窗口/系统集成    │
├─────────────────────────────────────────────────────┤
│              数据层:纯 Markdown 文件 + .kb/ 配置目录  │
└─────────────────────────────────────────────────────┘
              同步:Git / Syncthing(可插拔适配器)
```

### 各层技术选型

| 模块 | 推荐 | 理由 |
|---|---|---|
| 平台壳 | **Electron**(桌面)+ Capacitor(移动) | Obsidian 验证过的路线;核心写成纯 Web 应用,壳薄到可被 shim 替换 |
| 编辑器 | **CodeMirror 6 + @lezer/markdown** | 增量解析、装饰系统;Obsidian/思源/SilverBullet 的共同选择 |
| Live Preview | 自研 ViewPlugin(装饰层) | 六条模式:原文为源、光标感知、窄失效、行高恒定、冻结守卫、视口渲染 |
| 索引管线 | **remark/mdast + 自研 wikilink 扩展** | 批处理 AST,与编辑器解析器分开,各管各的 |
| 链接索引 | 内存正排 + 倒排 Map,Worker 增量维护 | 参照 Foam 的 Workspace/Graph/Provider 四层分离 |
| 全文搜索 | **SQLite FTS5 + Intl.Segmenter/jieba 预分词** | 中文必须预分词;FTS5 索引落盘免重建、BM25 排名 |
| 图谱 | Graphology + ForceAtlas2(Worker)+ Sigma.js(WebGL) | 小图可降级 d3-force + Canvas |
| 同步 | Git 三路合并 + 检测 `.sync-conflict` 给合并 UI | 可插拔适配器设计,学 Joplin 的 sync target 抽象 |
| 插件 | manifest.json + main.js,同进程 API + 能力网关 | 学 Obsidian 的极简格式,但从第一天收敛文件/网络访问 |

## 三、核心机制设计要点

### 1. Metadata Cache(照抄 Obsidian 模式)

- **纯内存、启动重建、事件驱动增量更新**——小中型库(数千文件)启动索引仅数百毫秒,完全不需要索引持久化的复杂度
- 文件 watcher 驱动:变更文件 → 重解析 → 先删旧出链再插新出链,**绝不全量重建**
- 两阶段事件:文件元数据就绪 → 链接解析完成(`resolved`)
- 未解析链接是一等公民(图谱虚拟节点 + "先链接后写作"工作流)
- 分层查询:**元数据走索引、全文走 FTS5**
- 兜底:网络盘/FUSE 等监听不可靠环境,加轮询对账

### 2. 编辑器 Live Preview(六条工程模式)

1. Raw markdown 是唯一真相,所见即所得 = Decoration
2. 光标感知:光标进入即展开源码 —— 体验的灵魂
3. 窄失效:只重建变化行的装饰
4. 行高恒定:隐藏语法符零宽化,无布局抖动
5. 鼠标冻结守卫:拖拽选择中不重建
6. 视口虚拟化:只渲染可见行

### 3. 双链索引数据结构

```ts
// 全部内存驻留,Worker 增量维护
basenameMap: Map<string, string[]>          // 短链解析(重名取最短路径)
outgoing:    Map<string, LinkOccurrence[]>  // 正排:文件 -> 出链(含位置)
backlinks:   Map<string, SourceOccurrence[]>// 倒排:目标 -> 源(反链面板数据源)
blocks:      Map<string, BlockLocation>     // ^block-id -> (file, offset)
aliases:     Map<string, string>            // frontmatter 别名 -> 文件
```

派生功能几乎免费:孤儿笔记(倒排为空)、断链(正排目标解析不到)、枢纽笔记(按入度排序)。

### 4. 未链接提及

第一期:**Aho-Corasick 自动机**对所有标题+别名做单遍精确匹配;语义/模糊匹配留作插件扩展点。

### 5. 插件系统

- 核心功能(文件浏览器、搜索、图谱、反链、模板)全部做成核心插件,与社区插件同 API——**官方 dogfood 是 API 质量的保证**
- 生命周期:`onload()`/`onunload()` + `register*()` 统一登记自动回收
- 宿主维护解析缓存,插件订阅 `changed` 事件而非各自重复解析(生态性能的关键)
- 信任模型:个人项目先走 Obsidian 式同进程高信任模型,但文件/网络访问收敛到可审计的 API 网关,为 Worker 沙箱留路

### 6. 同步(可插拔适配器)

- 抽象成 sync target 接口(学 Joplin):本地 Git、Syncthing 友好模式、未来官方服务
- 冲突策略:三路文本合并 > 双版本保留;检测到 `.sync-conflict-*` 文件时给合并 UI
- 若将来做付费同步服务,学 Obsidian Sync 的 E2EE 配方:scrypt → HKDF → AES-256-GCM,并公开派生参数 + 提供自验证脚本
- **铁律写进文档:不要同时跑两个同步引擎**

## 四、MVP 实施路线

### Phase 1:最小可用(2-4 周)

- [ ] Electron 壳 + 文件树 + CM6 源码编辑
- [ ] Markdown 渲染(reading mode,remark 管线)
- [ ] chokidar 文件监听 + 内存 metadata cache
- [ ] `[[wikilink]]` 解析 + 正排/倒排索引 + 反链面板
- [ ] basename 全局短链解析

### Phase 2:体验核心(4-6 周)

- [ ] Live Preview(装饰层六模式)
- [ ] SQLite FTS5 全文搜索(中文预分词)
- [ ] 链接自动补全、重命名时更新引用
- [ ] 未解析链接 → 占位笔记创建流
- [ ] 局部图谱(Canvas + d3-force)

### Phase 3:生态与健壮性(按需)

- [ ] 插件系统(先核心功能插件化,再开放)
- [ ] 全局图谱(ForceAtlas2 + Sigma.js)
- [ ] 同步适配器(Git 集成)
- [ ] 未链接提及(Aho-Corasick)
- [ ] Canvas 白板(JSON Canvas 格式)
- [ ] 性能工程:Worker 池、索引持久化、正文懒加载、插件懒加载

### 贯穿始终的原则

1. **纯文本为唯一事实源**,任何私有扩展可降级为可读文本
2. **平台壳要薄**,核心是与平台无关的 Web 应用
3. **一切皆插件**,官方功能与社区插件同 API
4. **开放格式是护城河**:Markdown + 开放的白板格式 + 可迁移配置
5. **性能归属可观测**:内置启动耗时分解,区分本体 vs 插件开销
6. **UI 状态入 store**,快照/撤销/会话恢复都变简单(学 TiddlyWiki)

## 五、可以直接抄作业的开源项目

| 想实现的功能 | 去读这个项目的代码 |
|---|---|
| 链接图索引的完整骨架 | **Foam**(Workspace/Graph/Provider/DataStore 四层,TypeScript,最易读) |
| Live Preview 编辑器 | **atomic-editor** / **codemirror-live-markdown**(Obsidian 式装饰层复刻) |
| 块级模型 + 内存图数据库 | **Logseq**(DataScript EAV 模型) |
| 同步抽象层 + E2EE | **Joplin**(sync target + item 加密边界) |
| 内容文件 + 派生索引两级存储 | **思源笔记**(.sy + SQLite,Go 内核) |
| CRDT 原生编辑器 | **BlockSuite**(Yjs 数据流) |
| 极简自举数据模型 | **TiddlyWiki**(一切皆 tiddler) |
| 生产级 FTS5 + 增量重索引 | **markdown-vault-mcp** |

建议的研读顺序:**Foam(最小完整骨架)→ atomic-editor(编辑器)→ Obsidian 官方 API 文档(插件系统)→ Joplin(同步)**。
