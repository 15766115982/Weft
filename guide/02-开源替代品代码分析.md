# 02 · 开源替代品代码分析

> 本文深入分析 8 个开源知识库/笔记项目的技术架构与代码设计。
> 阅读目的:这些项目**代码全部开源**,是可以直接 clone 下来研读的"教科书"。

## 总览对比表

| 项目 | 技术栈 | 事实来源(source of truth) | 双链粒度 | 同步方案 | 扩展机制 |
|---|---|---|---|---|---|
| Logseq(文件版) | ClojureScript / Rum / Electron | Markdown/Org 文件 + DataScript 内存库 | 块级(EAV datom) | 文件同步 / 官方 Sync | iframe 沙箱 JS 插件 |
| Logseq(DB 版,2.0) | 同上 | SQLite 单文件 | 块级 + 类型化属性 | RTC(块级冲突消解) | 插件适配 DB API |
| Joplin | Electron + React Native,monorepo | SQLite(WAL + FTS) | 笔记级链接 | 可插拔 sync target,delta + E2EE | 受限插件 API |
| Foam | TypeScript,VS Code 扩展 | Markdown 文件 | 文件级 wikilink(+块锚) | 不管(Git/网盘) | 宿主即平台 |
| SilverBullet | Rust 服务端 + TS/CodeMirror/Preact PWA | Markdown 文件 | 页面级 + 查询对象 | 全量镜像 + 轮询回写 | Plugs + Space Lua |
| TiddlyWiki | 纯 JS 微内核 | 单 HTML 内 tiddler store(或 .tid 文件夹) | tiddler 级(含转置) | syncer + adaptor(Node 服务端) | 一切皆 tiddler,自举 |
| AFFiNE | Web Components + Yjs;Rust OctoBase | CRDT(Yjs/y-octo)块树 | 块级 | CRDT P2P / WebSocket | BlockSuite 框架级扩展 |
| Anytype | Go 中间件 + 各端 UI | 本地对象图(CRDT) | 块级 + 对象关系 | any-sync:P2P + 加密中继,密钥自持 | API/协议级开放 |
| 思源笔记(SiYuan) | Go 内核 + TS/Electron | .sy JSON 文件 + SQLite 派生索引 | 块级(ID 引用) | AES 加密快照仓(官方云/S3/WebDAV) | petal 插件 + HTTP API |

**八种项目,事实来源只有四种答案**:

1. **纯文本文件**(Foam / SilverBullet / Logseq 文件版 / Obsidian)—— 生态与可读性最好
2. **数据库**(Joplin / Logseq DB 版)—— 查询与性能最好
3. **结构化文档 + 可重建派生索引**(思源的 .sy + SQLite)—— 两者折中,最务实
4. **CRDT 文档即数据库**(AFFiNE / Anytype)—— 协作原生,复杂度最高

## 1. Logseq:ClojureScript + DataScript 的"块即数据"大纲工具

### 技术栈

- 桌面端 Electron,几乎全部前端代码用 **ClojureScript** 编写,UI 层使用 **Rum**(React 的 ClojureScript 封装)
- 文档解析器用 **OCaml + Angstrom** 编写后交叉编译
- Git 集成靠纯 JS 实现的 **isomorphic-git**
- 嵌入 **sci**(Small Clojure Interpreter)安全求值用户脚本

### 存储模型:磁盘文件是事实来源,内存数据库是查询引擎

文件版中笔记以 Markdown / Org-mode 纯文本存储,磁盘文件是 source of truth。启动数据流:

```
磁盘/云加载文件 → 解析(必要时解密) → 灌入 DataScript(内存不可变数据库) → 初始化 UI 状态 → React 渲染
```

应用状态清晰地二分:

- **文档状态**(页面、块、内容)→ 全部存入 DataScript
- **UI 状态**(当前编辑的块等)→ 普通 Clojure atom
- Rum 组件响应式订阅两类状态,变化时高效重渲染

每次编辑触发三件事:① 写回磁盘/云;② 更新 UI 状态;③ 对 DataScript 执行 transaction 并重建查询缓存。

### 数据模型:一切皆 block,block 即 EAV datom

DataScript 中数据以 `[id attribute value]` 三元组(datom)存储。块是基本单元,**页面只是带 `:block/name` 属性的特殊块**:

```clojure
{:block/uuid #uuid "64909c2c-...",
 :block/parent {:db/id 1287},
 :block/refs [{:db/id 3} {:db/id 1295}],
 :block/content "A block that references ...",
 :block/format :markdown,
 :block/page {:db/id 1287},
 :db/id 1299}
```

- 大纲层级通过 `:block/parent` 表达
- 双链通过 `:block/refs`(解析 `[[link]]` 与 `#tag` 得到)表达
- 所有关系都是数据库里的引用边,**反向链接、块引用、标签、属性查询天然就是图查询**

### 双链/索引实现:Datalog 查询

查询语言是 **Datalog**(由 DataScript 提供),模式匹配形如 `[?block :block/page ?page]`。

最具特色的设计:**把内部查询语言直接暴露给用户**——"高级查询"让用户用和应用内部完全相同的 Datalog 查询和重塑自己的数据,用户与开发者使用同一套数据语言能力。

### 与 Obsidian 文件型模型的差异

- Obsidian:文件即真相 + 增量索引(内存缓存),Markdown 文件直接映射为一篇笔记
- Logseq:文件之上构建**统一的内存图数据库**,块是一等公民,可跨文件块级引用、嵌入和声明式查询
- 代价:启动要解析全部文件建库(大库较慢);文件落盘格式需与数据库模型来回映射(丢格式、frontmatter 兼容性问题的根源)

### 2025 年的重大转向:DB 版本(SQLite)

Logseq 2.0(Beta)推出 **DB graph**:存储从 Markdown 文件换成**单一 SQLite 数据库文件**,属性变为类型化实体、标签变为带 schema 的 class,支持画廊/看板视图和块级冲突解决的实时协作。

> **经验教训**:"文本文件 + 内存数据库双写"的映射复杂度,长期看可能超过直接以数据库为唯一事实来源。但 SQLite 单文件仍保住了本地优先和离线可用。

### 插件机制

- 插件基于 Web 技术,SDK 为 `@logseq/libs`(带 TS 类型),通过全局 `logseq` 命名空间暴露 API
- 入口 `logseq.ready(main)`,插件运行在 **iframe 沙箱**中与主窗口隔离
- 分发走 GitHub Release(zip)+ Marketplace

### 最值得借鉴

1. **不可变内存数据库作为查询层**:EAV datom 让"块、页、引用、属性"统一成图,反链/查询零额外成本;不可变数据结构白送撤销/历史
2. **内部查询语言开放给用户**:声明式查询是高级用户的杀手级功能
3. **状态二分**:文档数据进数据库、UI 状态进 atom,渲染层纯响应式订阅

## 2. Joplin:离线优先的 SQLite + 多端同步 + E2EE

### 技术栈

**Monorepo**:桌面端 Electron + React,移动端 React Native,另有 CLI 端与 Joplin Server(Node.js)。核心逻辑(数据模型、同步器、加密)抽在共享包中供各端复用——"一套核心、多端壳"。

### 存储模型:SQLite 为本地事实来源

笔记**不是**磁盘上的 Markdown 文件,而是存入本地 SQLite(`database.sqlite`),附件放 `resources/`:

- 开启 **WAL 模式**,写入时读不阻塞,同步过程 UI 流畅
- **FTS4/FTS5** 全文索引实现搜索
- 统一 **BaseModel/BaseItem** 抽象:笔记、笔记本、标签、资源都是带 GUID 的 item,为同步和加密提供统一处理面
- 短板:本地数据库默认不加密(at rest),E2EE 只保护"离开设备"的数据

### 同步方案:同步目标抽象 + 增量同步

- 同步做成**可插拔的"同步目标"**:Joplin Server/Cloud、Nextcloud、Dropbox、OneDrive、WebDAV、文件系统任选
- 同步器以 item 为单位,用**同步游标(sync cursor)记录进度,做 delta 增量同步**
- 本地 SQLite 是事实来源,同步目标只是(可能完全不可信的)传输/存储介质

### 端到端加密

- **SJCL** 实现 AES-128/256;主密钥由口令派生
- **每个 item 在上传前于客户端加密**,服务器只存密文;分享场景用 RSA 做密钥交换(WebCrypto)
- 解密由后台 `DecryptionWorker` 按需进行,支持主密钥轮换

### Web Clipper 与本地 HTTP API

浏览器扩展 + 桌面端内置**本地 HTTP API 服务**:扩展把网页 POST 到本地端口,桌面端写库。这个本地 REST API 后来成为整个第三方生态的入口——低成本撬动集成的经典手法。

### 最值得借鉴

1. **同步目标抽象层**:统一 item 模型 + delta 协议 + 可插拔后端,不绑死任何云
2. **E2EE 做在序列化边界上**:加密发生在 BaseItem 序列化处,业务代码几乎无感
3. **本地 HTTP API 服务器**:一个常驻端口同时支撑 Clipper 和第三方生态

## 3. Foam:站在 VS Code 肩膀上的双链知识库

### 为什么做成 VS Code 插件

定位极其清醒:**不重新发明编辑器**。VS Code 免费提供一流编辑器、文件树、全文搜索(ripgrep)、Git 集成、跨平台分发、市场生态。Foam 只补齐知识管理特有的三件事:**wikilink 解析、反向链接、关系图谱**。

### 核心抽象(来自仓库 CLAUDE.md,可直接研读)

- **FoamWorkspace**:中央资源仓库,管理所有 note/attachment;内部用**反向 trie** 做高效资源查找(支持 `[[note]]` 短链不写全路径);事件驱动(`onDidAdd/onDidUpdate/onDidDelete`),增量更新
- **FoamGraph**:维护资源间链接/反链图,随 workspace 实时更新;为悬空链接建 **placeholder 资源**(不存在的目标也入图)
- **ResourceProvider 模式**:可插拔资源解析层(`MarkdownProvider` / `AttachmentProvider`)
- **DataStore 接口**:抽象文件系统操作,可对接本地/远程/虚拟 FS
- **Feature 集成模式**:每个特性是 `(context, foamPromise) => void` 函数,注册 VS Code 命令与各类 Provider

### 双链如何"白嫖" VS Code 生态

VS Code 为编程语言设计的 LSP 式 API 与双链笔记需求几乎一一对应:

| 知识库功能 | 复用的 VS Code API |
|---|---|
| `[[wikilink]]` 跳转 | `DefinitionProvider` |
| 反向链接 | `ReferenceProvider` |
| 链接自动补全 | `CompletionItemProvider` |
| 重命名笔记时更新所有引用 | `RenameProvider` / workspace edit |
| 图谱/面板 | Webview + TreeView |
| 预览增强(note embed `![[note]]`) | markdown-it 插件 |
| 全文搜索 | 内建搜索(ripgrep) |
| 版本管理 | 内建 Git |

### 最值得借鉴

1. **宿主平台杠杆**:80% 通用能力外包给成熟宿主,自己只写领域核心
2. **Workspace / Graph / Provider / DataStore 四层分离**:文件监听 → 资源模型 → 链接图,全事件驱动、增量更新——**这套骨架几乎可以直接照抄**
3. **placeholder 幽灵节点**:悬空链接建幽灵节点,"创建新笔记"流极其顺滑,图谱也完整

## 4. SilverBullet:单用户却做成自托管 PWA 的"可编程"笔记

### 技术栈与总体架构

反直觉的架构:**明明是单用户工具,却做成自托管 Web 应用**。

- 服务端 **Rust**:提供文件/space 的 HTTP API、下发客户端 bundle、跑服务端 Lua 的 headless 运行时
- 前端 **TypeScript + CodeMirror 6 + Preact**,打包为 **PWA**

### 存储模型与离线设计

- 数据就是磁盘上一个文件夹里的纯 Markdown 文件(space)
- 两种客户端模式:
  - **online**:直连服务器读写
  - **synced**:整份 space 复制到浏览器本地存储,渲染、编辑、索引、Lua 全在浏览器端执行,**100% 离线**,重连后回写
- 同步采用**轮询而非 WebSocket**,换取实现简单

### Plug 系统与 Space Lua

- **Plugs**:插件机制,可扩展命令、编辑器、索引
- **Space Lua**:跑在笔记空间里的 Lua 方言,配合 **Live Queries(SLIQ)、Live Templates、Objects、Widgets**——用户在笔记里直接写脚本:动态列表、查询视图、自定义对象类型(任务、联系人)都是"数据 + 内嵌脚本"的产物
- 索引器为带 frontmatter 属性的页面/对象建索引,Live Query 直接查询这些对象

### 最值得借鉴

1. **"单用户 + B/S 架构"不矛盾**:服务端薄、客户端厚,天然得到浏览器/手机/PWA 多端访问,省去 Electron
2. **客户端全量副本 + 极简同步**:不做 CRDT,"整库镜像 + 回写"达成离线优先——个人场景复杂度收益比极高
3. **内嵌脚本即扩展**:Lua 沙箱 + Live Query 把插件平民化,用户不写 JS 也能定制

## 5. TiddlyWiki:单 HTML 文件里的一切皆 tiddler

### 微内核架构

SPA 的极致:**整个应用(代码 + 逻辑 + 数据)装在一个 HTML 文件里**,可从 `file://`、U 盘直接运行。

- JS 微内核(`boot/boot.js`)极小,内核之外的一切——核心模块、插件、主题——都是 **tiddler** + **wikiText**
- 整体呈 MVC:
  - **Model**:tiddler store(以标题为键的 key-value 存储)
  - **View**:widget 渲染树;DOM 被当作"只写",任何区域随时可从 store 重建
  - **Controller**:核心代码发出 store-change 事件,触发刷新周期

### 一切皆 tiddler 的数据模型

tiddler 是原子信息单元,本质是带 `fields` 的对象:`title`、`text`、`tags`、`created`、`modified` + 任意自定义字段。

- **用户内容、插件、主题、UI 状态全都是 tiddler**;系统条目用 `$:/` 前缀做命名空间
- 由于 UI 状态也在 store 里,**整个界面在任何时刻都可由 store 重建**——单文件保存因此成为平凡操作:序列化 store ≈ 序列化整个应用状态
- **wikiText**:自有标记语言,支持宏、transclusion(内容转置/嵌入);链接指向 tiddler 对象而非地址,**重命名不会断链**
- **filter 语言**:声明式查询语言(`[tag[xxx]]`),系统 UI(侧边栏、搜索结果)本身就用 filter 写成——"TiddlyWiki 是用 TiddlyWiki 实现的"

### 保存与同步的取舍

- **单文件模式**:所有 tiddler 存 HTML 内隐藏 DIV,保存时**整文件重写**。优点:极致便携、零依赖、复制文件即备份;缺点:对版本控制极不友好、并发编辑无解、库越大保存越重
- **Node.js 服务器版**:`tiddlywiki --listen` 起内建 HTTP 服务,tiddler 落盘为独立 `.tid` 文件;浏览器端通过 sync adaptor 做近实时同步(skinny tiddler 元数据列表对比、按需懒加载正文)

### 最值得借鉴

1. **数据模型的极简与自洽**:一个 fields 字典承载万物 + 通用查询语言,系统功能自举于同一套原语
2. **状态可序列化 = 应用可持久化**:UI 状态入 store,"保存整个应用"变平凡
3. **命名空间化系统数据**(`$:/`):用户数据与系统数据同库不同域,扩展机制异常统一
4. **清醒的取舍示范**:单文件牺牲 diff 友好与协作,换来分发的终极简单——架构没有银弹,只有明确的价值排序

## 6. AFFiNE:CRDT 原生的块编辑器 + Rust 数据引擎

### BlockSuite(编辑器框架,Web Components)

- 对标 Notion + Miro;BlockSuite **框架无关**,基于原生 Web Components(类似 Monaco 之于 VS Code)
- 最大特色:**不用事件溯源,直接用构建在 Yjs 之上的 CRDT 块树("YModel")作为唯一事实来源**
- 所有更新——本地编辑、历史回退、远端协作——走同一条 Yjs 事件管道,应用代码**不需要区分更新来源**;时间旅行近乎零成本,实时协作开箱即用
- 渲染层不假设 DOM:同一 store 同时驱动文档 UI 和 **canvas 白板渲染器(Edgeless)**,文档与白板双模态共享一份数据
- 分层:headless 框架(`@blocksuite/store`、`@blocksuite/inline`、`@blocksuite/block-std`)+ 预制组件(`@blocksuite/blocks`、`@blocksuite/presets`)

### OctoBase(后端数据引擎,Rust)

- 协作后端基于 **y-octo**(Yjs 的 Rust 对应实现),数据结构与 BlockSuite 兼容
- 能力:离线可用的协作存储、二进制去重存储、多语言分词实时全文索引、CRDT 驱动的 P2P 同步(WebSocket / WebRTC / libp2p)、细粒度权限
- 存储无关:SQLite / Postgres 适配器,可嵌入式也可独立部署

### 最值得借鉴

1. **"CRDT 作为唯一数据模型,而非同步附加层"**:多数产品是"数据模型 + 事后接 CRDT",BlockSuite 反其道而行,撤销、协作、离线三难问题一并化解
2. **headless 编辑器框架 + 预制组件分离**:store/选区/命令系统做成无 UI 内核,渲染层可换(DOM 或 canvas)
3. **同构 CRDT 前后端**(Yjs ↔ y-octo):同步协议就是 CRDT update 交换,协作后端复杂度大降

## 7. Anytype:any-sync 协议与"密钥在用户手里"的本地优先

### 技术栈与数据模型

- 中间件层 `anytype-heart` 用 **Go** 编写,各端 UI 共享这一核心
- 数据模型是**对象-类型-关系(Object-Type-Relation)图**:一切都是带类型的对象(笔记、任务、人),对象由块组成,对象之间以关系连接——"块编辑器 + 结构化数据库 + 图谱"合三为一

### any-sync 协议(核心亮点)

开源同步协议,逐条对标 Ink & Switch 的本地优先七条理想:

- **No spinners**:每个 space 的主副本在本机,同步在后台安静进行
- **网络可选**:完全离线可用,可在局域网内直接同步
- **无缝协作**:CRDT 让每台设备独立消解冲突
- **The Long Now**:厂商消失应用仍可用(协议与代码开源)
- **默认安全**:端到端加密,备份节点存的是自己读不了的密文,冲突消解在本地设备发生
- **终极所有权**:12 词恢复短语在设备端派生密钥,服务器零知识

### 同步拓扑

- 同一局域网设备**直连 P2P 同步**
- 跨网络靠**中继/备份节点**转发与存储密文,配合 seed/discovery 节点做设备发现(可完全自托管,官方提供 docker-compose 部署整个网络)

### 最值得借鉴

1. **同步协议独立成开源产品**:any-sync 是可复用协议 + 可自托管网络组件——把同步层当公共品设计
2. **加密与身份合一**:恢复短语派生密钥即账号,无密码、零知识服务器
3. **对象-类型-关系图模型**:比"页 + 块"多一层类型系统,笔记、数据库视图、图谱查询共用同一存储

## 8. 思源笔记(SiYuan):Go 内核 + 块级双链的本地优先系统

### 技术栈与总体架构

- **B/S 风格前后端分离**:Go 编写的常驻内核,监听 `127.0.0.1:6806` 的本地 HTTP 服务器,承担全部业务逻辑与持久化
- 前端 TypeScript + Electron(浏览器亦可直接访问)
- Go 的好处:goroutine 高并发、单二进制部署、移动端复用同一内核
- 编辑器引擎为自研 **Lute**(结构化 Markdown 引擎,Go 与 JS 双实现)

### 存储模型:.sy JSON 文件 + SQLite 索引

```
工作空间/
├── data/      明文笔记数据(.sy 文件)
├── history/   明文历史版本
├── repo/      加密、分块、压缩的快照(本地历史与云同步用)
├── temp/      siyuan.db(SQLite)、blocktree 索引、日志
└── conf/      配置
```

- 笔记本是文件夹,**每篇文档是一个 `.sy` 文件,内容为 JSON**;有子文档时配同名文件夹
- **文件/文件夹以块 ID 命名**(14 位时间戳 + 7 位随机字符,如 `20240405123456-abc123.sy`),原因:规避各 OS 文件名限制、允许同级同名文档、保证历史版本唯一
- 每个块有唯一 ID,块树直接序列化为 JSON:`{id, type, content, children[], created, updated}`
- SQLite 存放**索引/查询数据**(块引用关系、全文搜索),是从 `.sy` 重建的派生物——**索引损坏不丢数据**

### 双链实现:块 ID 为锚的细粒度引用

- **双链以块 ID 为引用目标**:`[[` 可搜索块命名/别名/内容,可引用任意段落、列表项、表格
- 锚文本可自定义且**不因目标标题变化而失效**(引用只认 ID)
- ID 与时间戳编码、全局唯一且永不复用,链接稳定性极高,文档可随意重命名/移动

### 同步方案

- 本地 `.sy` 明文**不直接参与云同步**;真正上传的是 `repo/` 里 **AES 加密的变更日志与快照**(密钥仅存本地,E2EE),支持官方云 / S3 / WebDAV
- 官方明确**反对用第三方网盘直接同步 data 目录**(易损坏数据)——数据交换一律走快照仓格式

### 最值得借鉴

1. **"内容文件 + 派生索引"两级存储**:`.sy` JSON 是事实来源,SQLite/搜索索引可随时重建——兼顾可读性与查询性能
2. **块 ID 即文件名的彻底 ID 化**:用不可变 ID 承载一切引用,把"重命名/移动/同名"这些老大难问题一次性消灭
3. **本地 HTTP 内核 + 薄前端**:前后端彻底解耦,浏览器、Electron、移动端、第三方脚本共用一个内核——调试时甚至可以直接 curl 自己的笔记

## 9. 总体启示(给自研知识库的 7 条经验)

1. **先选事实来源,再谈功能**。文本文件换生态与可读性,数据库换查询与性能,"文件 + 可重建索引"是折中里最务实的。
2. **链接要用不可变 ID,不要用标题/路径**。思源块 ID、TiddlyWiki 对象引用、Logseq datom 引用都证明:以名字为锚的链接必然要为重命名付出工程代价。
3. **把查询语言做成一等公民**。Datalog(Logseq)、filter(TiddlyWiki)、Live Query(SilverBullet)、SQL(思源/Joplin)殊途同归:知识库的复利来自"可编程的检索"。
4. **同步是复杂度之王,按规模选武器**:单人→文件镜像/快照;多端单人→delta + 游标;协作→CRDT。**不要为单人场景过早引入 CRDT**。
5. **加密做在序列化边界上**(Joplin item 加密、思源 repo 快照、Anytype 密钥层级),业务代码保持明文思维。
6. **能白嫖就白嫖**:Foam 证明宿主平台可承包编辑器、搜索、Git、分发;思源证明"薄前端 + 厚内核"能让第三方生态免费长出来。
7. **UI 状态入 store 则一切皆快照**(TiddlyWiki / DataScript),撤销、离线、单文件分发都会变简单。
