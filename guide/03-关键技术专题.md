# 03 · 关键技术专题

> 本文按技术专题纵向深挖构建"类 Obsidian"知识库所需的各项核心技术。
> 每个专题包含:核心原理、主流方案对比、选型建议、参考来源。

## 专题 1:Local-first 软件原则

### 原理

奠基性文献是 Ink & Switch 实验室(Martin Kleppmann、Peter van Hardenberg 等)2019 年发表于 ACM Onward! 的论文 **《Local-First Software: You Own Your Data, in Spite of the Cloud》**。

核心论点:云应用(Google Docs、Trello)给了我们实时协作和多设备访问,但剥夺了数据所有权——服务关停,数据即亡。Local-first 软件把**本地设备上的数据副本视为权威副本(primary copy)**,服务器只持有协助同步的次要副本。

七条"理想"(ideals):

1. **No spinners(即刻响应)**:所有读写都在本地完成,无网络往返
2. **Your work is not trapped on one device(多设备)**:联网时数据在所有设备间同步
3. **The network is optional(离线可用)**:离线功能完整,恢复连接后 opportunistic 同步
4. **Seamless collaboration(无缝协作)**:实时协作体验不输云应用——**最难实现的一条**
5. **The Long Now(数据长存)**:数据生命周期超过应用和厂商
6. **Security and privacy by default(默认安全隐私)**:端到端加密,服务器只存自己读不懂的数据
7. **You retain ultimate ownership and control(用户终极控制)**:可自由复制、修改、导出

论文指出 **CRDT 是实现 local-first 的使能技术**——"天生多主"的数据结构,允许不同设备的并发修改无需中央权威即可合并。

### 本地优先 vs 云服务的取舍

- **收益**:零延迟、离线可用、数据自主、隐私默认、长期可迁移(纯文本格式加分)
- **代价**:同步与冲突合并复杂度转移到客户端;"分享一个链接"的协作模式需要额外基础设施;备份责任部分转移给用户;iOS 后台同步受限
- **工程现实**:Obsidian 选择"纯本地文件 + 可选付费 E2E 同步服务"的折中;Logseq/Anytype 走 CRDT/P2P 路线。七条理想是渐近线而非全有全无

### 选型建议

以七原则作为架构 checklist:文件格式用纯文本 Markdown(满足 Long Now);所有功能离线可用;同步层做成可插拔;若上服务器同步则 E2E 加密。**协作功能可后置,因为它是最贵的一条。**

## 专题 2:同步与冲突解决

### CRDT 原理与两大库对比

CRDT(Conflict-free Replicated Data Type)满足"交换律、结合律、幂等"合并语义:多个副本各自离线修改后,任意顺序合并都收敛到同一状态。

| 维度 | Yjs | Automerge |
|---|---|---|
| 底层算法 | YATA(clientID + 单调序号) | RGA 变体(actorID + 序号) |
| 数据模型 | 抽象类型(Text/Array/Map/XML),偏编辑器 | 任意嵌套 JSON 文档,Git 式完整变更历史 |
| 包体积/内存 | ~18 KB JS,轻量 | Rust/WASM 核心 ~320 KB(Automerge 3 后文档小 10 倍) |
| 同步协议 | state vector 增量同步,增量包最小 | Bloom filter 变化集交换;`automerge-repo` 传输抽象 |
| 生态 | 最大(Tiptap、ProseMirror、Quill、Lexical 绑定;Notion、Linear 使用) | TS 类型更好、学习曲线平缓 |
| 历史 | 只存结果文本 + 合并元数据 | 存全量编辑历史(可时间旅行) |

> 经验结论:**做协作编辑器选 Yjs;做通用 JSON 文档同步/版本历史选 Automerge**。新库 Loro、学术界的 Eg-walker 也值得跟踪。

### 文件级同步 vs 块级实时协作

- **文件级同步**(Git、Syncthing、Obsidian Sync、iCloud/WebDAV):以整个文件为同步单元,冲突粒度粗。Git 能做行级三路合并;Syncthing 只能生成 `.sync-conflict-<时间戳>` 副本文件让用户手工合并
- **块/字符级实时协作**(CRDT/OT):以字符或块为合并单元,多人同改一文件也能自动收敛,可携带光标/选区 awareness 信息。代价是实时通道与"CRDT 文档 ↔ 纯文本文件"的映射问题

Obsidian 生态实际对比:

| 维度 | Syncthing | Git(Obsidian Git 插件) |
|---|---|---|
| 加密 | 设备间 TLS 直连,无云端副本 | 无 E2E,明文躺在 Git 托管商 |
| 冲突处理 | 双版本保留 + `.sync-conflict` 文件,手工合并 | 真正的三路合并 + 完整历史 |
| 同步方式 | 实时连续 | 手动/定时 commit-pull-push |
| 移动端 | Android 好,iOS 弱 | 移动端"极不稳定" |
| 设备要求 | 需同时在线(或常驻节点) | 经中央仓库解耦 |

> ⚠️ **绝不要两个同步引擎同时写同一 vault**——这是社区中最常见的 vault 损坏原因。

### 冲突处理策略谱系

1. 最后写入赢(LWW)——最简单,适合设置类字段
2. 文件级双版本保留(Syncthing 式)——安全但打断用户
3. 三路行级合并(Git)——对 Markdown 文本效果出人意料地好
4. CRDT 自动合并——体验最佳、成本最高
5. 应用层"修改前确认对端干净" + 文件锁/版本向量——务实折中

### 选型建议

分两层:**默认提供文件级同步适配器(Git 三路合并 + 检测 `.sync-conflict` 给出合并 UI);CRDT 只在确定要做实时协作时引入**,且优先用 Yjs 绑定编辑器(CodeMirror 有 y-codemirror.next),避免自己发明格式。

## 专题 3:双链(backlinks)的实现原理

### wikilink 解析

`[[wikilink]]` 不是 CommonMark 标准语法,需要在解析层扩展。Obsidian 支持的完整语法族:

```
[[Note]]            基本链接
[[Note|alias]]      别名显示
[[Note#heading]]    标题锚点
[[Note#^blockid]]   块引用
![[embed]]          嵌入(transclusion)
```

两条实现路线:

1. **正则/词法扫描**:`\[\[([^\]|#]+)(#[^\]|]+)?(\|[^\]]+)?\]\]` 直接扫纯文本。简单快速,但会误匹配代码块、行内代码里的文本,需要排除规则
2. **AST 扩展**:mdast 体系写 micromark 扩展(社区有 `mdast-util-wiki-link`),或在 Lezer 语法中加 token。天然避开代码块,位置信息精确,利于编辑器高亮和跳转

> **建议:索引管线用 AST 提取(准确),输入时自动补全等快速场景用轻量正则。**

### 链接索引:正排 + 倒排

backlinks 索引本质是**特化的倒排索引**:全文索引映射 `词 → 文档`,backlink 索引映射 `链接目标 → 源文档`。

标准做法:

1. 解析每个文件提取所有出链 → **正排索引** `note → [outgoing links]`(记录每个链接位置,供上下文显示)
2. 反转得 **倒排索引** `target → [sources]`——这就是反链面板的数据源
3. **链接解析(resolution)**:Obsidian 规则是"最短路径匹配"——`[[Note]]` 匹配全库任意路径下名为 Note 的文件,重名时取路径最短者。需维护 `basename → [paths]` 映射
4. **增量维护**:监听文件变更,只重解析变更文件,先按旧出链从倒排表删除该源条目,再插入新出链。**绝不能全量重建**
5. **重命名处理**:改文件名时遍历倒排索引,重写所有指向它的 wikilink 文本
6. 派生功能几乎免费:**孤儿笔记**(倒排为空)、**断链**(正排目标解析不到)、**枢纽笔记**(按入度排序)

### 未链接提及(unlinked mentions)

Obsidian 的实现出乎意料地朴素:**精确短语匹配,而非模糊匹配**。

- 为每篇笔记构造"引用 ID 集合"(笔记名、文件 basename、frontmatter aliases)
- 全库 grep 这些字符串(大小写不敏感、整词),出现在正文中但未被 `[[ ]]` 包裹即为未链接提及
- 已知边界问题:别名互为子串时重复建议;代码块内误报;Zettelkasten 式标题匹配靠 aliases 解决

性能要点:对 N 个标题 × M 篇文档做朴素子串扫描是 O(N×M×文本长),上万文件不可接受。工程做法:

- 把所有标题+别名建成 **Aho-Corasick 自动机**,单遍扫描全库文本即得所有命中
- 或先经全文索引检索标题词缩小候选文档集,再在候选内精确匹配
- 若要"模糊"提及:社区方案是 Damerau-Levenshtein 距离或 BM25+向量混合检索(RRF 融合)

### 块引用(block reference)

- **Roam 模式**:块是数据库一等公民,每块天生有 UID,引用即指针,双向编辑。但存储是私有图数据库,不可移植
- **Obsidian 模式(Markdown 友好)**:块 ID 是显式标注——段落末尾追加 `^block-id`;`[[note#^id]]` 引用,`![[note#^id]]` 嵌入。嵌入内容是**只读副本**,编辑须回源头
- 实现:解析器把 `^id` 识别为块元数据存入索引 `block-id → (file, offset)`;渲染嵌入时按索引取源块 AST 子树内联渲染
- **取舍:纯文本上做不到 Roam 的双向等价块,这是为文件可移植性付出的本质代价**

### 选型建议

```
索引结构(全部内存驻留 + 持久化缓存,文件 watcher 驱动增量更新):
├── Map<basename, paths[]>          短链解析
├── Map<file, LinkOccurrence[]>     正排
├── Map<target, SourceOccurrence[]> 倒排(反链数据源)
└── Map<blockId, location>          块引用表
```

未链接提及第一期做 Aho-Corasick 精确匹配,语义匹配留作插件扩展点。

## 专题 4:Markdown 解析与编辑器

### 两条解析路线

**A. remark/unified 生态(批处理 AST)**

- unified 是 AST 处理总线,remark 提供 Markdown 支持,AST 格式为 mdast
- 管线:`remark-parse`(MD→mdast)→ 变换插件(remark-gfm、remark-frontmatter、remark-math、remark-wiki-link)→ `remark-rehype` → hast → HTML
- 底层 micromark 是 CommonMark 兼容的逐字解析器,生态极其庞大(数百插件)
- **特点:输出完整 AST,适合索引/转换/发布管线;但每次解析全量,不适合编辑器内每击键重解析**

**B. CodeMirror 6 + Lezer(增量解析)**

- Lezer 是 Marijn Haverbeke 为 CM6 写的增量解析系统:LR(可选 GLR)生成器 + 运行时
- 编辑后通过 `TreeFragment` 复用旧语法树未变部分,重解析代价 O(变化范围);自带错误恢复
- Markdown 因非上下文无关,`@lezer/markdown` 是**手写增量解析器**,用 WeakMap 给块节点附加上下文(缩进、列表记号)判断哪些节点可安全复用
- **增量解析真正解决的是编辑器内"每击键都要语法树"的延迟与 GC 压力**(全量解析对单篇笔记其实够用)

### Live Preview(所见即所得)的技术要点

Obsidian 式 live preview = **源码是唯一真相 + 装饰层(decoration)**,而非双向文档模型(那是 Typora/Slate 路线,状态同步极痛)。

六条核心模式:

1. **Raw markdown is the source of truth**:文档内容永远是纯 markdown;所有所见即所得只是 ViewPlugin 根据 Lezer 语法树发射的 `Decoration.mark()`(加样式)和 `Decoration.replace()`(隐藏语法标记、替换为渲染 widget,如图片、公式)
2. **光标感知**:仅当光标/选区不在节点内时才隐藏语法标记;进入即"展开"回源码——**这是 Obsidian 体验的灵魂**
3. **窄化失效(narrow invalidation)**:装饰重建只触及内容变化的行,编辑复杂度 O(change size)
4. **无布局抖动**:inline 装饰不改变行高;替换型 widget(图片)用固定占位高度
5. **鼠标冻结守卫**:拖拽选择进行中不重建装饰,避免打断交互
6. CM6 视口机制(只渲染可见行)让大文档渲染天然高效

### 选型建议

- 编辑器选 **CodeMirror 6**(Obsidian 本体即 CM6,无可争议)
- 编辑器内解析用 `@lezer/markdown`(增量),扩展解析 `[[wikilink]]`、`#tag`、`^blockid` 为自定义 token
- **索引/导出/图谱管线另用一套 mdast/remark**——两套解析器各司其职,不要试图复用
- Live preview 按上述 6 条模式实现 ViewPlugin

## 专题 5:全文搜索

### 方案对比

| 库 | 类型 | 适用规模 | 特点 |
|---|---|---|---|
| **FlexSearch** | JS 内存索引 | ~10 万文档 | 基准碾压级;支持 Web Worker、索引可持久化;API 相对繁琐 |
| **MiniSearch** | JS 内存索引 | ~5 万文档 | Lunr 的现代替代:索引更小、模糊/前缀/自动补全、**支持增量增删文档**;API 友好 |
| **Lunr** | JS 内存索引 | ~1 万文档 | 老牌、静态站点标配;不支持模糊、索引不可增量更新;新项目不建议 |
| **SQLite FTS5** | 嵌入式 DB | 百万级+ | 10 万记录查询 ~2.9ms;BM25 排名、增量合并、索引落盘免重建;需 SQLite 环境(Electron/移动端天然可用,浏览器可 wa-sqlite/absurd-sql) |

### ⚠️ 中文/CJK 是一票否决项

FTS5 默认 unicode61 分词器按空白/标点分词,**对中文完全失效**(整段中文被当成一个词)。可行解:

- (a) FTS5 **trigram 分词器**(SQLite 3.34+):子串匹配可行,但索引大、无语义分词
- (b) **预分词**:写入索引前用 jieba/nodejieba 把中文切成空格分隔的词
- (c) 可加载分词扩展(如 sqlite-simple-tokenizer,支持中文+拼音)

MiniSearch/FlexSearch 同样默认拉丁分词,需自定义 `tokenize` 函数接 jieba 或 **Intl.Segmenter**(浏览器原生,轻量够用)。

### 选型建议

- **Electron/桌面自研知识库:首选 SQLite FTS5 + 中文预分词**——索引持久化(启动不重建)、增量更新、BM25 排名、规模天花板最高
- 纯 Web/浏览器端:**MiniSearch** + Web Worker 建索引 + 序列化到 IndexedDB;极限性能再上 FlexSearch
- 模糊搜索另配 Fuse.js 或 MiniSearch fuzzy;语义搜索作为独立扩展(向量嵌入 + RRF 融合)

## 专题 6:图谱可视化

### 原理

力导向布局:节点建模为质点,节点间施加斥力(many-body),边上施加弹簧引力,迭代至能量收敛。

- 朴素斥力全对计算 O(n²),标配优化是 **Barnes-Hut 四叉树近似**(远处节点群聚合为质心,O(n log n),d3-force 的 `forceManyBody` 内置)
- 调参杠杆:`theta`(近似程度,调大更快更糙)、`distanceMax`(截断远程斥力)、`alphaDecay/alphaMin`(提前收敛停机)

### 大规模图(上万节点)方案对比

**布局算法层**:

- d3-force:Barnes-Hut,够用但非最快
- **d3-force-sampled**:随机顶点采样(RVS),O(n),比 Barnes-Hut 快约 2.9 倍且质量无损
- **ForceAtlas2**:Gephi 系算法(graphology-layout-forceatlas2),**Obsidian 图谱即此类布局**,社区结构更美观
- GPU 路线:cuGraph GPU ForceAtlas2 可交互跑 10 万+节点

**渲染层**(EuroVis 基准):

- SVG:节点过 5000 帧率趋零
- Canvas 2D:可到约 1–2 万
- **WebGL(Sigma.js、PixiJS、Three.js):万级标配**——Sigma.js+Graphology 实测 2.9 万节点 ~100FPS

**架构模式**:布局与渲染分离——力模拟放 **Web Worker**,主线程只做 WebGL 绘制与交互(拾取用颜色编码离屏渲染);超大图可预计算布局落盘。

### 选型建议

- 局部图谱(数百节点):Canvas + d3-force 即可
- 全局图谱(万级):**Graphology + graphology-layout-forceatlas2(Worker 内)+ Sigma.js(WebGL 渲染)** 是最成熟开源组合;自绘省事可用 vasturiano/force-graph
- 必做优化:默认只显示局部图谱/按入度过滤 Top-N;模拟收敛后停 tick;标签只在足够缩放级别渲染

## 专题 7:插件系统设计

### 两种信任模型

**Obsidian 模式(无沙箱,信任+审核)**

- 插件是与宿主同进程的任意 JavaScript,继承应用全部权限(读写文件系统、联网、执行程序)
- 官方明确"无法限制插件权限",缓解措施:
  - 默认 Restricted Mode 屏蔽一切第三方代码
  - 社区插件上架人工初审
  - **2025 年起每个版本自动化安全扫描**(此前只审首次提交,更新从不复审,是重大缺口)
  - 热门插件持续人工复审;计划中:能力声明(网络/文件/剪贴板)、作者认证
- 残余风险:minified 发布代码可与源码不一致、作者账号被盗推送恶意更新、数千无人维护插件

**VS Code 模式(进程隔离,但同样无权限沙箱)**

- 所有扩展运行在独立 **Extension Host 进程**(Node),RPC 与渲染主进程通信;扩展崩溃不拖垮 UI
- API 声明式:扩展只能调用 `vscode.*` 命名空间,不能直接碰 DOM,所有 UI 能力经 API 中介
- 注意:**VS Code 扩展同样拥有完整 Node 权限**,隔离是为稳定性而非安全
- 副产品红利:远程开发时扩展宿主可跑在远端(Remote Extension Host)

### 对比

| 维度 | Obsidian | VS Code |
|---|---|---|
| 隔离 | 无,同进程 | Extension Host 独立进程(为稳定性) |
| 权限 | 全部 | 全部(Node) |
| UI 扩展 | 直接操作 DOM(自由但脆弱) | 只能走声明式 API/webview(稳定但受限) |
| API 表面 | `App/Vault/Workspace/MetadataCache/Editor` 对象 + 事件 | `vscode.*` 命名空间 + 激活事件 + contribution points |
| 审核 | 初审 + 每版本自动扫描 | 市场审核 + 签名 |

### 自研插件 API 设计要点

1. **分层信任**:核心 API 只暴露能力对象(vault 读写、metadata 查询、编辑器命令、UI 注册点),不暴露原始 require/process;文件访问收敛到 vault 根内
2. **声明式贡献点**:命令、设置页、视图、状态栏、编辑器扩展都通过 manifest 注册,宿主控制生命周期(onload/onunload、懒激活)
3. **事件驱动缓存**:MetadataCache 模式——宿主维护解析缓存,插件订阅 `changed` 事件而不是各自重复解析文件(**这是 Obsidian 插件生态性能的关键设计**)
4. **沙箱分级**:低权限插件跑 Web Worker/iframe,高权限插件明示授权
5. 版本化 API + 弃用周期,避免生态碎裂

### 选型建议

个人项目起步走 **Obsidian 式同进程 API + 明确文档化的能力边界**(开发体验最好、生态门槛最低),但从第一天就把插件对文件/网络的访问收敛到可审计的 API 网关后面,为未来升级 Worker 沙箱留路。照搬 VS Code 全进程隔离成本高,除非要做远程/多端架构。

---

## 专题 8:性能工程(大型 vault)

### 症状与瓶颈(真实社区数据)

- 万级文件后,启动索引与全局搜索明显退化;Android 上 1.3 万笔记无插件索引需 3–4 分钟
- 12.6 万文件的 vault 出现每次打开全量重索引;10 万+ 文件在 Electron 4GB 内存上限处冻结
- **关键洞察:问题不在文件数,而在触发全量重建的变更频率与范围**;Obsidian 按 mtime 判断重索引,批量导入脚本若改时间戳会强制全量重建

### 优化策略

**启动速度**:

1. **索引持久化**:启动 = 加载缓存索引 + diff mtime/size 增量重解析变更文件,绝不从零重建
2. **插件延迟加载**:按"启动必需/按需"分组懒加载(社区 Lazy Plugin Loader 可压到 1 秒内)
3. **渐进式渲染**:先渲染 UI 骨架与上次会话状态,索引在后台 Worker 完成,边索引边可用

**索引建立**:

4. **Worker 化**:解析、分词、链接索引全部放 Web Worker 池,完全不阻塞 DOM
5. **批处理事务**:IndexedDB 瓶颈是事务开销而非吞吐——单事务写 1000 条 ~80ms vs 每写一事务 ~2s
6. **排除机制**:.gitignore 式文件忽略,大图/附件不进索引

**内存**:

7. **正文懒加载**:内存只驻留元数据 + 索引(标题、链接、标签、块 ID),正文按需读盘、LRU 缓存
8. **语法树与装饰视口化**:CM6 只解析/渲染可见区域
9. 注意 Electron 单进程堆上限,必要时把索引移入 SQLite(磁盘即内存扩展)——absurd-sql 实测比裸 IndexedDB 快约 10 倍

### 选型建议

架构基线:

```
文件 watcher(chokidar)→ 任务队列 → Worker 池解析
    → SQLite(FTS5 + 链接表 + 元数据表)持久索引
    → 内存只放热数据
```

启动目标:10 万文件 vault 冷启动 <2s 可用,索引后台秒级完成。始终提供"安全模式(禁插件)启动"作为排障基线。
